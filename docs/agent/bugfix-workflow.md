# 버그 수정 워크플로우

1. **재현**: 정확한 재현 절차 확보. 어떤 도메인/화면/요청인지 특정.
2. **계층 좁히기**: [observability](../engineering/observability.md)의 디버깅 표로 UI / api / client / offline / mocks 중 어디인지 좁힌다.
3. **근본 원인**: 증상이 아니라 원인을 찾는다. 특히 인증 루프·오프라인 폴백·캐시/큐는 `client.ts`·`offline/*`를 함께 본다.
4. **최소 수정**: 범위를 최소화. 횡단 로직(`client.ts`)은 다른 도메인에 영향 → 신중히.
5. **회귀 방지**: 가능하면 테스트 추가([testing-strategy](../engineering/testing-strategy.md)). 러너 없으면 재현 절차를 PR에 기록.
6. **검증**: `pnpm verify` + 재현 절차로 수동 확인.
7. **문서**: 원인이 문서/규칙의 빈틈이었다면 해당 문서 보강.

## 위험 신호 (사람 확인)

- 오프라인 쓰기 큐의 중복/유실 가능성.
- 인증/토큰 만료 처리 변경.
- 데이터 마이그레이션/스키마 영향.
